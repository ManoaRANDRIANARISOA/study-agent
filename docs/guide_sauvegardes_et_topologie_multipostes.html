Guide Opérationnel & Architectural

Sauvegardes & Architecture Multi-Postes

Procédures officielles pour la gestion des données, la résilience aux pannes, l'évitement des régressions anachroniques et l'intégrité de la caisse scolaire dans Study Agent.
💡
L'Axiome Fondamental de Study Agent :
Le fichier SQLite (study_agent_{ecole_id}.db) présent sur un ordinateur local est un RÉPLICAT CACHE HORS LIGNE. Le MASTER UNIQUE ET DÉPOSITAIRE de l'établissement est le Cloud Supabase (PostgreSQL).

1 Topologie Multi-Postes dans l'Établissement

Dans un établissement type, plusieurs ordinateurs interagissent simultanément avec la même base école :

Poste Caisse (Guichet POS)

Émet les reçus légaux, encaisse les frais de scolarité, gère le tiroir-caisse et effectue la clôture journalière (Ticket Z).

Poste Secrétariat

Enregistre les nouveaux élèves, met à jour les coordonnées parents, saisit les présences et les dispenses médicales.

Poste Direction / Comptabilité

Supervise les tableaux de bord, valide les fiches de paie, verrouille les trimestres et consulte les totaux consolidés.

2 Le Piège Mortel : "La Régression Anachronique" (Time-Travel Split-Brain)

⚠️
INTERDICTION FORMELLE : NE JAMAIS RESTAURER UNE ANCIENNE COPIE SQLITE LOCALE SUR UN POSTE CONNECTÉ.

Démonstration du désastre causé par une restauration manuelle :

  1. Vendredi 17h00 : Le caissier copie manuellement study_agent_ecole.db sur une clé USB.
  2. Lundi à Mercredi : Les Postes 1, 2 et 3 fonctionnent normalement. 150 paiements sont enregistrés et synchronisés sur le Cloud. Le compteur de reçus passe de REC-00100 à REC-00250.
  3. Jeudi 08h00 : Le Poste 1 plante. Le technicien prend la clé USB du vendredi et écrase le fichier SQLite du Poste 1 avec la sauvegarde de 5 jours plus tôt.
  4. Conséquences Immédiates :
    • Doublons de numéros de reçus : Le compteur local de Poste 1 revient à 100 ! Il réémet les numéros de reçus REC-00101, REC-00102 déjà donnés à d'autres parents le lundi précédent.
    • Rejeu d'écritures fantômes : Si la sauvegarde contenait des écritures en attente dans sync_queue, celles-ci sont réinjectées sur Supabase et décomptent l'argent deux fois.
    • Écrasement LWW (Last-Write-Wins) : Le Poste 1 écrase les fiches élèves mises à jour le mercredi par le Secrétariat avec ses vieilles données du vendredi.

3 Le Piège Technique : Mode WAL SQLite sous Windows

Study Agent configure SQLite en mode WAL (Write-Ahead Logging) pour supporter les écritures concurrentes et la vitesse :

%APPDATA%\study-agent\
├── study_agent_ecole_dev.db          (Fichier principal - Pages de base)
├── study_agent_ecole_dev.db-wal      (Journal WAL - Transactions récentes non checkpointées)
└── study_agent_ecole_dev.db-shm      (Mémoire partagée / Verrous d'index)
⚡
Pourquoi la copie de fichier à chaud échoue :
Si un utilisateur ou un script de sauvegarde copie uniquement study_agent_ecole_dev.db pendant que l'application tourne : toutes les transactions récentes présentes dans le .db-wal sont perdues et la base restaurée sera marquée comme corrompue (erreur disk I/O error ou database disk image is malformed).

La seule méthode valide pour copier SQLite à chaud :

Utiliser l'API atomique intégrée de better-sqlite3 :

// Exécuté dans le process Main sans verrouiller l'application
await db.backup(path.join(cleUsbPath, `backup_ecole_${Date.now()}.db`))

4 Procédures Opérationnelles Officielles

Scénario A : Panne d'un Poste (Internet Disponible)

Le disque dur d'un PC a grillé ou Windows est réinstallé.

  • Installer l'application neuve sur le PC de remplacement.
  • Saisir les identifiants de l'école (Tenant : ecole_dev).
  • Cliquer sur "Réhydratation Complète Propre" (Full Pull).
  • En 3 à 5 minutes, le Cloud régénère une base SQLite 100% à jour.
  • NE JAMAIS copier un ancien fichier SQLite depuis une clé USB.

Scénario B : Coupure Internet Prolongée (> 1 Semaine)

L'école tourne entièrement hors ligne sans accès 4G.

  • Utiliser le bouton officiel dans l'app : "Exporter sauvegarde atomique".
  • L'application appelle db.backup() et valide le checkpoint WAL.
  • La clé USB est conservée dans le coffre-fort de la direction.
  • Ne restaurer cette sauvegarde qu'en cas de crash total simultané de TOUS les PC hors ligne.
  • Si un seul PC a déjà resynchronisé avec le Cloud, interdiction formelle de restaurer.

5 Matrice des Bonnes et Mauvaises Pratiques

Action Envisagée Statut Raison / Risque Technique
Réinstaller l'application et lancer un Full Pull Cloud RECOMMANDÉ Garantit la conformité stricte avec l'état validé par les autres postes.
Copier le fichier .db d'un poste vers un autre poste STRICTEMENT INTERDIT Provoque la duplication des codes guichets et écrase les séquences de reçus.
Copier study_agent.db à chaud par Explorateur Windows STRICTEMENT INTERDIT Omet le fichier WAL : corruption de base garantie à la restauration.
