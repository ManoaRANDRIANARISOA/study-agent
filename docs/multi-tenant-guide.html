Guide Architecture SaaS : Study Agent Multi-Tenant (Option A)

Documentation officielle sur le fonctionnement centralisé de la base de données.

1. Le concept du SaaS Multi-Tenant

Study Agent est conçu pour héberger un nombre illimité d'établissements scolaires en utilisant une seule base de données Supabase partagée (le Cloud).

  • Une seule base, un seul schéma : Au lieu d'avoir 50 bases de données pour 50 écoles, toutes les données vont dans les mêmes tables (students, users, payments...).
  • Le passeport ecole_id : Pour que les données ne se mélangent pas, absolument chaque ligne de chaque table possède une colonne ecole_id.
  • Sécurité Absolue (RLS) : Supabase utilise le Row Level Security (RLS) de PostgreSQL. Il est techniquement impossible pour l'école A de voir les données de l'école B, car la base de données filtre automatiquement toutes les requêtes SQL avec WHERE ecole_id = [ID_DU_CLIENT].

2. L'Installation chez un Client (Zero-Config)

L'installation chez un nouveau client a été grandement simplifiée. Il n'y a plus aucun script en ligne de commande à exécuter manuellement.

  1. Le Premier Lancement : Le client installe l'exécutable (.exe) sur son ordinateur. Sa base SQLite locale (study_agent.db) est totalement vierge.
  2. L'Onboarding Automatique : L'application détecte que la base est vierge et affiche l'interface de "Premier Démarrage" (FirstBootOnboarding.tsx).
  3. Création de l'Administrateur : Le directeur renseigne son propre identifiant ("admin") et son propre mot de passe.
  4. Génération de l'Empreinte (UUID) : C'est le moment magique ! En arrière-plan, le logiciel génère un UUID ultra-sécurisé et aléatoire pour être le nouvel ecole_id exclusif de ce client. Cet identifiant est stocké dans la table settings locale et lie définitivement le logiciel.
Aucun risque de collision

Parce que chaque directeur créé son compte depuis l'Onboarding, l'ID généré pour ce compte et pour l'école est unique au monde. Ainsi, même si l'École A et l'École B utilisent toutes les deux "admin" comme identifiant, elles coexisteront pacifiquement sur Supabase, séparées par leur ecole_id unique.

3. Comment faire évoluer le logiciel (Nouvelles Colonnes)

Lorsqu'une norme ou une option spécifique est demandée par un (ou plusieurs) client(s), vous devez modifier les deux bases de données pour qu'elles restent un miroir parfait.

  • Étape 1 (Local) : Créez un fichier de migration SQLite (ex: src/main/database/migrations/034_add_nouvelle_colonne.sql) pour ajouter la fonctionnalité sur l'ordinateur des clients existants via une mise à jour.
  • Étape 2 (Cloud) : Allez sur le Dashboard Supabase (SQL Editor) et tapez manuellement votre commande ALTER TABLE. C'est fait une bonne fois pour toutes pour l'ensemble des écoles actuelles et futures !

Rappel : Si une colonne ne concerne que l'école C, elle restera vide (NULL) pour l'école A et B. C'est normal et recommandé.

4. Que contient le fichier setup_multi_tenant.sql ?

Ce fichier historique servait à convertir une ancienne architecture mono-établissement (LMS) en architecture Multi-Tenant. Il se charge d'ajouter la colonne ecole_id sur toutes les tables existantes et d'activer le filtre de sécurité RLS.

Attention au fichier supabase_full_schema.sql

Le fichier scripts/supabase_full_schema.sql est le schéma "Maître" qui représente l'état exact de la base Cloud avec la règle UNIQUE(username, ecole_id) pour la table des utilisateurs.

5. Auto-Seeding (Données par défaut pour les nouveaux clients)

Livrer une application avec une base de données totalement vide (0 classe, 0 matière) offre une mauvaise expérience au premier lancement. Pour pallier cela, le système peut utiliser l'Auto-Seeding.

  • Le Principe : Juste après la création du compte Administrateur lors de l'Onboarding, l'application peut proposer au client de pré-charger une "Configuration Standard" (ex: Primaire, Collège, Lycée).
  • L'Injection : Si accepté, l'application injecte silencieusement dans la base SQLite locale les données par défaut (ex: matières "Maths", "Français", Rôles de base).
  • Pour les Démos : Pour générer une instance de démonstration complète, vous pouvez exécuter node scripts/clone_test_db.js. Cela clonera vos données LMS existantes et assignera un ecole_id automatiquement en contournant l'Onboarding.

6. L'Outil SuperAdmin (Générateur Marque Blanche)

L'interface SuperAdminBuilder est un outil interne caché, conçu strictement pour vous (le créateur) afin de générer des exécutables .exe sur-mesure (Marque Blanche) pour des clients VIP. Il modifie le .env et lance la compilation npm run build:win.

Comment y accéder (Mode DEV uniquement)

Cet outil n'existe pas dans l'application finale compilée. Pour l'ouvrir en phase de développement :

  1. Lancez l'application en mode développement (npm run dev).
  2. Ouvrez la console développeur (F12 ou Ctrl + Maj + I).
  3. Tapez la commande suivante puis faites Entrée :
    window.location.hash = '#/superadmin'

Vous serez instantanément téléporté sur l'interface de création.
